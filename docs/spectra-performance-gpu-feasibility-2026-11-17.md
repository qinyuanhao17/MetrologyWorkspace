# Spectra Viewer 提速与 GPU 可行性方案

建议先落地 CPU 并行嵌入准备，再做独立的 GPU 绘图试验。此次仅进行了只读测试和方案评估，正式程序与 v5.3.2 Release 没有修改。下面的并行耗时属于原型实测；GPU 绘图尚未进行帧率或图像一致性验收。

本机为 Ryzen 7 4800H，8 核 16 线程，约 16 GB 内存；系统枚举到 AMD Radeon 核显与 NVIDIA GTX 1650 约 4 GB 独显，并有远程显示适配器。Windows 原生隐藏上下文实际创建成功，报告 AMD Radeon / OpenGL 3.3。因此有接入 GPU 绘图的硬件基础，但不能把系统枚举到的 GTX 1650 当成程序当前使用的显卡。

**已测得的导入收益**

读取 `D:\spectra`，扫描 4809 个 SME；3123 个成功读取，1686 条读取 issue 保留，不因本次提速评估更改筛选/解析规则。可读取部分共 3129 个 Channel，数值与波长数组合计 499,256,848 字节。此前整批读取耗时 14.881 秒、嵌入准备 13.920 秒，其中 zlib 压缩 11.374 秒。

同一进程中加载一次源数组，按 1、2、4、8 线程顺序各运行两次。每个任务只处理一个文件，采用现有的 metadata JSON、NumPy 容器、zlib level 1 和 Base64 格式；比对完整输出顺序及所有记录的 SHA-256，全部与原串行结果逐字节相同。

| 并发数 | 第一次 / 秒 | 第二次 / 秒 | 中位耗时 / 秒 | 相对串行 |
|---|---:|---:|---:|---:|
| 1 | 13.318 | 13.425 | 13.371 | 1.00× |
| 2 | 7.616 | 7.696 | 7.656 | 1.75× |
| 4 | 4.757 | 4.615 | 4.686 | 2.85× |
| 8 | 3.767 | 3.802 | 3.785 | 3.53× |

这是此机器、此批数据的两次重复观测，不是其他机器上的保证，也不是整个导入流程的倍数。整批读取、建树、分组和首屏绘图仍需另外计时。此次未测峰值内存或交互延迟；4、8 只是本机已测配置，不能用来规定所有电脑的 Auto 上限。

Auto 应按资源预算扩展：`并发数 = min(CPU 预算, 内存允许并发数, 可并行任务数)`，最低为 1。CPU 预算从进程实际可用的 CPU 资源出发，考虑物理核心、逻辑处理器及运行限制；性能优先可先以可用物理核心数作为候选，平衡模式预留部分资源。内存预算应扣除源数组、输出结果、界面和其他工作的占用，再依据单任务峰值确定并发上限；限制在途任务，避免一次提交整批导致内存堆积。

例如有 32 个可用物理核心、内存充足且任务很多时，性能优先 Auto 应允许评估 32 个工作线程，不因本机只测试到 8 而固定封顶。逻辑线程数高于物理核心数时，是否进一步增加并发由实测吞吐决定。多个模块同时运行时共享 CPU 预算，避免解析、压缩和绘图分别占满全部资源。

硬件预算可作为首版 Auto 的基础；进一步可以在同一类任务的可比较批次中评估提高并发的吞吐收益，收益饱和或界面/内存压力增加时停止升档，并用滞回避免频繁波动。这种反馈调优是后续可选增强，不应把它假定为所有线程池自带的功能。保留手动覆盖，以适应其他工作负载和不同机器。

日常导入不进行额外性能测试，不重复压缩同一批文件来选线程。默认 Auto 采用平衡策略，依据可用核心数、内存和文件数量直接决定本次并发，并为界面及其他程序预留 CPU 预算。使用所有物理核心或逻辑线程可能与界面、绘图和其他程序争用 CPU、内存带宽等资源；多核机应允许提高并发，但“允许评估到核心数”不等于默认总是占满。

性能测试的时机分为开发验证与可选校准：开发时在代表性硬件上比较并发档位；用户可以主动运行一次性能校准，以少量代表性数据比较候选值并保存结果。校准不在每次导入时自动运行；应用升级若改变压缩实现或用户更换硬件，可将已有校准标记为需要重新确认，在重新校准前继续使用硬件预算规则。普通导入至多利用正在进行的真实工作记录耗时和资源压力，不为测量重新处理已完成数据。首版不需要实现在线升档，优先保证规则可预测、界面响应及取消语义正确。

结果保存在本机 `.cache/spectra-import-20261117/parallel-all.json`、`all-4809.json` 和 `gpu-context.json`。所有脚本先隔离设置，再读取样本；生产设置哈希保持当前值，原始数值数组哈希一致。

**第一阶段：导入优化，可行性高，改动范围较小**

1. 在现有后台加载流程中按文件并行压缩，限制在途任务和内存，保留输出顺序。取消后停止提交新任务、丢弃未完成批次，现有 Viewer 数据继续保留。失败不得发布半份嵌入数据。
2. 状态分别显示扫描、读取和嵌入准备的完成数；增加当前阶段耗时，按节流频率更新，避免向界面发送大量事件。
3. 尊重 Paths Only 模式。当前加载线程只检查 `_workbook_embedded`，没有检查 `spec_save_type`，因此路径模式仍可能做不需要的预打包。路径模式应跳过此阶段；嵌入模式继续保证工作簿脱离 SME 原文件后可恢复。
4. 独立评估“读取一个文件、随即后台压缩”的流水线，让读取与压缩重叠。尚未测得其端到端收益，不能承诺整批导入会降到某个固定秒数。
5. 再次导入时，可评估基于已验证内容标识的编码缓存复用；必须包含格式版本和失效规则。不得只凭文件名复用，也不得用缓存改变原有文件身份/筛选规则。

Python 的 zlib 在压缩时会释放 GIL，因此上述按文件多线程具备实际并行基础；本机重复测量也验证了收益。[Python 官方说明](https://docs.python.org/3.10/c-api/init.html)。

这一阶段保持既有无损格式，避免为了提速引入新的工作簿格式。SQLite BLOB、去 Base64 或替换压缩算法应另立格式迁移方案，包含新旧版本读写、恢复、损坏校验和旧文件兼容性，不并入第一阶段。

**第二阶段：GPU 绘图试验，可行性中高，适配成本中高**

当前使用 PyQt6 6.11 / Qt 6.11.1 / pyqtgraph 0.14.0。密集曲线先在 CPU 子进程中生成 QImage，再由界面显示缓存；视口变化可能触发几何准备、跨进程传递与重新栅格化。GPU 优先解决拖动、缩放和选择重绘。

Qt 支持以 QOpenGLWidget 作为 Graphics View 视口；pyqtgraph 0.14.0 已更新曲线 shader 绘图路径。[Qt 官方说明](https://doc.qt.io/qt-6/graphicsview.html)，[pyqtgraph 0.14.0 发布说明](https://github.com/pyqtgraph/pyqtgraph/releases/tag/pyqtgraph-0.14.0)。

本项目不能直接全局打开 `useOpenGL` 后发布。除 CPU raster cache 仍占主要工作外，`_MulticolorViewportCurve` 与 `_HighlightViewportCurve` 还会创建仅供手工 paint 的内部曲线。这些内部曲线没有正常挂入 ViewBox；已安装版本的 `PlotCurveItem.paintGL()` 在取不到 ViewBox 时会直接返回。适配时必须覆盖批量绘图和 Highlight 两条路径。

建议保留现有 Qt/PyQtGraph 的坐标轴、布局、选择、Legend 与窗口管理，给曲线层增加可切换的 GPU 后端：

- 按坐标轴批量组织绘制；使用共享顶点缓冲、分段索引和颜色表表示多文件/多组曲线。保留 NaN 断点和每条曲线的身份映射。
- 源数据和 CPU 计算继续使用原精度；GPU 显示采用局部坐标和适当的显示缓冲，验证大偏移、小残差及深度缩放下的精度。GPU 缓冲不成为导出或统计的数据源。
- 平移、缩放尽量更新坐标变换；选择/Highlight 尽量只更新成员索引及样式，避免重传全部原始数组。
- Highlight 保留 7.5 px Halo 和 3.2 px Core 的屏幕尺寸及绘制顺序。宽描边采用可控的三角形几何，避免仅依赖驱动的宽线实现；OpenGL 不保证任意线宽均可用。[Microsoft OpenGL 文档](https://learn.microsoft.com/en-us/windows/win32/opengl/gllinewidth)。
- 共享波长和可复用缓冲，设置显存预算与释放策略；16 图和 Floating Plot 不各自复制整套源数据。具体显存占用需在原型中测量。
- 加入 Auto / CPU / GPU 选择和实际 Renderer 信息。上下文创建失败、远程桌面或驱动不兼容时，回退既有 CPU 绘图。需分别测试核显、独显及当前远程会话。
- Native Export 继续从完整源数组绘制；验证 GPU 屏幕与导出的范围、数据位置、颜色分组、透明度和 Highlight 层级。抗锯齿边缘可存在渲染器差异，需预先定义 GPU 图像验收尺度，不能据此削弱原 CPU 路径测试。

先在一个 M12 窗口中验证，再扩展到超过 32 Group、Primary/Secondary、16 个 Mueller、N/C/S、Psi/Delta、Reflectance、Floating Plot。业务层的 Wafer/SME 分组、3 Sigma、Residual、勾选与文件身份保持原语义。

**GPU 计算和压缩的优先级**

| 方向 | 适合解决的问题 | 建议 |
|---|---|---|
| OpenGL 曲线渲染 | 缩放、拖动、密集曲线和 Highlight 重绘 | 优先做可切换试验 |
| CuPy / CUDA 数值计算 | 经 profile 证实的大规模重复统计或数组计算 | 后续按实际热点决定，核对精度与搬运开销 |
| nvCOMP GPU 压缩 | 很大批数据的无损打包 | 当前优先级低；先采用已实测有效的 CPU 多线程 |

CuPy 需要关注初始化、数据驻留和异步计时；应测完整流程并用 GPU 事件计时，不能仅测发起任务的 CPU 耗时。[CuPy 官方性能说明](https://docs.cupy.dev/en/stable/user_guide/performance.html)。

nvCOMP 技术上提供 GPU 无损压缩，但引入 CUDA/驱动依赖、缓冲搬运、显存预算及格式兼容性工作。官方提供多种不同压缩格式；不能把 GDeflate 或 Bitcomp 直接当成现有 zlib 记录替换。[nvCOMP 官方文档](https://docs.nvidia.com/cuda/nvcomp/)，[安装要求](https://docs.nvidia.com/cuda/nvcomp/installation.html)。本机未进行 nvCOMP 吞吐测试。

**验收与决策顺序**

先交付 CPU 并行、分阶段进度、取消和路径模式修复，再决定 GPU 后端是否进入正式版本。CPU 第一阶段需重复整批导入并测首屏可用时间、主线程最长阻塞、取消延迟、峰值内存和保存恢复一致性。

GPU 试验需分别记录冷启动、首次上传和暖缓存交互。建议以高密度真实 4×4 Mueller 为主要验收场景，设“交互达到 30 FPS、Highlight 的 p95 响应低于 100 ms”作为待验证目标，不作为已实现收益；同时覆盖正确性、导出、重复开关与关闭后释放。原有完整回归仍需运行。

如果 GPU 没有优于当前 CPU 缓存，或不能满足样式与稳定性要求，则保留 CPU 为默认后端。此次可确定的收益是 CPU 并行打包；GPU 的交互收益必须由后续原型证明。
